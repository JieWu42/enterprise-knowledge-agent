# 需求与成功标准

目标用户是需要查询企业制度的员工。输入为问题和可选对话历史，输出为回答、文档 ID 与版本日期、原文引用、资料缺口和任务状态。

范围为报销、差旅、请假等 8 份合成短制度。没有纳入资料的规则不能依据模型常识补充；企业制度事实不借助互联网查询。暂不做 UI、在线部署或自动外部操作。

成功标准：

1. 明确问题可根据成功读取的原文回答，引用准确。
2. 冲突时补查适用范围，不按版本日期擅自裁决；无法消解则列出冲突及缺口。
3. 相似问法和上下文追问仍能取到对应证据。
4. 无资料、工具失败、模型失败、执行超限均明确报告；失败读取不能授权引用。
5. 至少两种真实运行路径展示模型观察工具结果后调整动作。
6. 可执行测试和实际运行材料可复现，Mock 与真实模型结果分开。

## 本人提出与确认的业务边界

吴杰提出，遇到两份期限不同但缺少适用范围和替代关系的制度，回答应说明这些信息缺失。实施中将此转成列出双方证据、不擅自选取新版本的边界。

吴杰提出复合问题“今年是否有带薪年假，具体如何申请”。首轮实际运行暴露了部分有依据但整体标为 answered 的状态问题。吴杰选择增加 partially_answered：保留已知流程，明确资格待确认。AI 协助实现和回归，详见贡献记录。

## 状态契约

| 状态 | 含义 |
| --- | --- |
| answered | 用户明确请求均得到证据支持，gaps 为空 |
| partially_answered | 仅部分请求可回答，有对应证据及未解决项 |
| needs_clarification | 适用范围或制度冲突尚需确认 |
| incomplete | 资料外、工具/模型不可用、超限或无法形成合法结果 |

状态准确性是验收对象，不以回答篇幅或措辞流畅代替。
